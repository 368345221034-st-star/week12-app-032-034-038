แดชบอร์ด **Streamlit** ที่ห่อ _"โมเดลสุดท้ายของทีม"_ ให้พนักงานโรงแรมใช้ประเมินได้จริง

## โมเดลและผลการวัด

- **โมเดลสุดท้าย:** Random Forest 60 ต้น (จำกัดความลึก 12, ใบขั้นต่ำ 3) — 22 ฟีเจอร์
- **ความแม่น:** ชุดทดสอบ 20% = **0.7923** · 3-fold CV = **0.7719** · precision 0.714 · recall 0.408 · F1 0.519
- **เทียบเส้นอ้างอิง:** Dummy (ทายคลาสใหญ่) = 0.7251 → โมเดลดีกว่าเส้นอ้างอิง ~6.7 จุด
- **ที่มาของ 22 ฟีเจอร์:** 16 ตัวคัดเลือกด้วย GA (จาก 72) + 6 ตัวที่กรอกในแอปได้จริง (ราคาเฉลี่ย/คืน, ประวัติยกเลิก, จำนวนครั้งที่แก้การจอง, จำนวนคืนวันธรรมดา/วันหยุด, จำนวนผู้ใหญ่)
- **ทำไมไม่ใช้ทั้ง 72 ฟีเจอร์:** ได้ความแม่นสูงกว่า (RF = 0.8486) แต่ต้องกรอก 72 ค่าในแอปซึ่งทำจริงไม่ได้ — งานนี้จึงเลือกชุดที่กรอกได้จริง (16 ช่อง) แล้วชดเชยด้วยการเพิ่ม 6 ฟีเจอร์ที่กรอกง่าย
- **ฟีเจอร์สำคัญที่สุด:** ระยะเวลาจองล่วงหน้า 22.6% · ช่องทาง Online TA 19.1% · คำขอพิเศษ 13.9% · ราคาเฉลี่ย/คืน 9.1% · มัดจำแบบไม่คืน 8.8%

## ตัวอย่างการทดสอบจริง (ในแอป)

| สถานการณ์ | ผลที่ได้ |
|---|---|
| จองล่วงหน้า 500 วัน · ราคา 200 · เคยยกเลิก 3 ครั้ง · พัก 4+2 คืน | **77.7%** → มีแนวโน้มยกเลิก (ควรโทรยืนยัน/เก็บมัดจำ) |
| จองล่วงหน้า 5 วัน · ราคา 80 · คำขอพิเศษ 4 อย่าง | **34.1%** → มีแนวโน้มมาเข้าพัก (ดูแลตามมาตรฐาน) |

## วิธีรันในเครื่อง

```powershell
cd <โฟลเดอร์โปรเจกต์>
pip install -r requirements.txt
streamlit run app.py
```

เปิด http://localhost:8501 (หรือดับเบิลคลิก `run.bat`)

## ข้อจำกัดที่ทีมบันทึกไว้

1. ข้อมูลเป็นชุดปี 2015–2017 ของโรงแรม 2 แห่ง (City/Resort) — โรงแรมอื่นควรทดสอบใหม่
2. คลาสไม่สมดุล (ยกเลิก 27.5%) → ดู precision/recall ประกอบ ไม่ดูแค่ accuracy (recall ของคลาส "ยกเลิก" = 0.408 แปลว่ายังพลาดเคสจริงบางส่วน)
3. โมเดลถูกคัดฟีเจอร์เพื่อลดภาระการเก็บข้อมูล จึงแลกความแม่นบางส่วนเมื่อเทียบกับโมเดลที่ใช้ทั้ง 72 ฟีเจอร์
4. ควรใช้ร่วมกับดุลยพินิจของทีมสำรองห้องพัก ไม่ใช่ตัดสินใจแทนคน
